SOURCE-BASED CODE REVIEW · LOCAL SNAPSHOT

四个终端 AI Agent 的 Harness 实现对比

对照 06 Architecture 的六项：Agent Loop、Context & Prompt、Tool Orchestration、State & Memory、Permission & Policy、Verification & Recovery。本页以当前工作目录中的源码为依据，强调“在哪里实现、由谁承担、工程取舍是什么”。

核心结论：四个项目共享相似的 Agent Loop，但 Harness 的边界完全不同。Claude Code 将能力集中在产品级 CLI；OpenClaw 把 Loop 委托给 Pi，自己做 Gateway 与多渠道编排；Pi 将运行时做成可复用积木，并把权限外包给部署环境；Hermes 则把记忆、审批、验证、恢复做成更完整的自主运行平台。

3. Skills：如何管理，如何进入 Agent Loop

Skill 是跨越六个模块的一种“可复用工作流资源”：它通常不是直接替代 Tool，而是给 Agent 提供按任务加载的操作说明、脚本、模板和引用资料。四个项目都避免在启动时把所有正文塞进上下文，差别在于发现、选择和注入的责任归属。

共同的运行链路：① 启动 / reload 时发现 SKILL.md 并读取 frontmatter → ② 只把名称、描述、位置等轻量目录暴露给模型 → ③ 用户命令或模型按任务匹配选择 Skill → ④ 在当前轮将正文注入，或通过读文件 / 专用工具按需读取 → ⑤ 下一次 Loop 调用模型时，Skill 指令与工具结果一起影响行动。
因此：Skill 管理解决的是“何时知道有能力、何时加载流程”；Tool 管理解决的是“如何真正执行动作”。
项目发现与管理模型最初看到什么如何进入 Loop安全 / 成本控制
Claude Code
多层目录 + 动态发现
managed、user、project、legacy command 目录可并存；按优先级去重。带 paths 的 Skill 可在触及匹配文件后被激活。
Skill listing
系统提醒中给模型列出可用 Skill；描述存在截断预算，避免目录本身吃满上下文。
SkillTool 调用
模型调用 SkillTool；默认将展开后的 prompt 注入主会话，也可按 Skill 配置 fork 成隔离子 Agent。
权限与隔离
Skill 有权限请求 / safe property 判定；fork Skill 有独立 token budget。已调用 Skill 记录可跨 compaction 保留。
OpenClaw
workspace / bundled / managed / plugin
解析 SKILL.md，按配置、环境和 Skill filter 做 eligibility；可生成 snapshot，保证一次 run 的 Skill 视图稳定。
<available_skills> 目录
名称、描述、绝对/压缩路径；超预算先退化为 name + location，再必要时截断数量。
Pi runner 的上下文输入
buildWorkspaceSkillsPrompt() 生成目录并传给 embedded Pi run；模型随后用 read 工具按路径读取正文与相对资料。
资格过滤 + prompt budget
有前置条件、disable-model-invocation、大小上限和 watcher 刷新；避免不可用或过大的 Skill 常驻 prompt。
Pi
资源加载器 + 目录优先级
递归识别 SKILL.md；项目的 .pi/skills / .agents/skills 与用户目录共同进入 ResourceLoader，并有 package / trust 管理。
XML 元数据目录
formatSkillsForPrompt() 写入 name、description、location；标记 disableModelInvocation 的 Skill 不暴露给模型。
read 或显式命令展开
模型按目录使用 read 工具；用户的 /skill:name args 会把正文包装为 <skill> 块，成为下一轮 user message。Agent Harness API 也支持 skill(name)。
信任边界 + 可见性开关
项目 Skill 可受 trust manager 约束；通过 disable-model-invocation 防止模型自动挑选，只允许应用/用户显式调用。
Hermes Agent
本地、外部、插件与 Hub
扫描 ~/.hermes/skills 与只读外部目录；插件 Skill 使用命名空间；可同步 / 安装 Hub 中的 Skill。
缓存的紧凑索引
build_skills_system_prompt() 生成索引，并使用进程 LRU + 磁盘 snapshot；可按分类降级为仅名称。
skills_list / skill_view 工具
Loop 可先列元数据，再用 skill_view(name) 拉完整正文；同一工具还可读取 Skill 内的 references/templates/scripts。
环境过滤 + 注入扫描
按平台、工具 / toolset 前置条件过滤；对正文做 prompt-injection 信号检查，并支持 Skill frontmatter 的 allowed-tools 约束。
Skill 在 Loop 中的四种形态“加载”并非只有一种语义；这决定它影响模型的范围和成本。

1 · 目录注入（四者共有）

把 name / description / location 写入系统提示。模型知道“有这项能力”，但不承担完整正文 token 成本。Pi 与 OpenClaw 的 XML <available_skills> 形式最直观；Hermes 使用紧凑索引；Claude Code 使用 Skill listing。

2 · 按需正文加载

Pi / OpenClaw 引导模型用 read 工具读取 SKILL.md；Hermes 用 skill_view；Claude Code 用 SkillTool。正文进入当前对话历史，随后一轮模型按其中步骤继续工具调用。

3 · 显式触发与隐式匹配

显式方式包括 Claude Code 的 slash Skill、Pi 的 /skill:name、Hermes 的用户/Agent 调用。隐式方式由模型根据描述挑选；Claude Code 还支持按 touched paths 激活条件 Skill。

4 · 作用域与执行模型

大多数 Skill 在主 Loop 中改写后续行为。Claude Code 特别提供 fork 模式，可把 Skill 放进子 Agent；OpenClaw 可为定时任务绑定 Skill；Hermes Skill 还可包含关联文件与可控预处理。

4. 六项 Harness 能力：经典问题盘点

以下不是功能列表，而是架构评审与 Benchmark 最值得追问的问题。每项列出 3 个高频、高杠杆问题，并给出可观测信号与首选治理手段。

01 · Agent Loop让模型持续行动，也必须让它在正确时刻停下。

停止标准是什么？

模型说“完成”不等于任务完成。文本回答、文件变更、测试通过、外部副作用与人工确认，都需要不同的完成定义。

信号：最终回复与验收物不一致
治理：exit contract＝任务断言、成功证据、步骤/时间/成本上限与用户中止。

如何避免无限 / 无效重试？

失败后反复调用同一工具、只改措辞不改假设，或观察结果没有新增信息，是最常见的“看似在工作”。

信号：相同 tool+args、错误签名或状态重复
治理：retry budget、去重键、进展度量、错误分类后换策略；无改善即升级给人。

Planning & Replanning 如何不失控？

长任务需要计划来维持方向，但计划又不能僵化：工具失败、新证据或约束变化后，何时局部修正、何时推翻重排？

信号：死守过期计划；频繁重规划却没有可验证进展
治理：计划应含里程碑、依赖、验收条件与假设；每轮以新证据触发局部 replan，并保留变更原因。

02 · Context & Prompt把有限 token 分配给此刻真正决定行动的信息。

超长输入如何处理？

日志、文档、附件会挤爆上下文；简单截断常恰好删掉错误位置、约束或输入输出边界。

信号：context overflow；模型遗漏关键约束
治理：分块检索、结构化抽取、token budget；保留目标/约束/最新观察，并允许按需重读原件。

Long-horizon task 如何不跑偏？

跨数十轮后，旧决策、失败尝试、陈旧观察与当前目标混在一起，Agent 容易重做已完成工作。

信号：重复探索；已解决问题复发；计划漂移
治理：显式 task state / plan / progress file；按阶段重述目标、验收条件与风险。

Context Compression 如何保真？

压缩会丢失文件细节、失败原因与未决条件；错误摘要甚至会成为后续推理的“假事实”。

信号：压缩后重复调查或引用错误历史
治理：结构化摘要（已证实/未证实/工件/命令/下一步）；保留原始工件并做完整性检查。

03 · Tool Orchestration工具不是函数列表，而是带状态、权限和观察语义的行动面。

工具选择：过多怎么选，如何发现新工具？

工具和 schema 越多，越容易误选、编造参数；同时，运行时新接入的 MCP、插件或项目工具，如何被安全发现并在恰当时机暴露给模型？

信号：invalid args、tool not found、错误工具调用；新能力长期不可见或被错误自动启用
治理：按任务阶段动态收窄工具集；以 capability metadata / registry 发现新工具；清晰描述与 schema，并经可信来源、权限和 read/write 策略过滤。

Tool Failure Recovery 如何设计？

超时、限流、参数错误、权限拒绝与部分成功，分别意味着不同的恢复路径；盲目重试会放大失败或制造重复副作用。

信号：同类错误重复；timeout 后外部状态未知；错误被压扁为一段文本
治理：按 transient / permanent / ambiguous 分类；先查询真实状态，再退避重试、换工具/参数、补偿回滚或升级给人。

结果如何管理？

空输出、异步任务或含糊错误会诱导模型提前宣布成功；而超长日志、列表或页面内容又会淹没上下文、挤掉任务约束。

信号：后台任务未结束即下结论；大段输出挤爆上下文，关键错误行被忽略
治理：结构化 result：status、证据、artifact、error；区分 submitted/running/completed/failed；超长结果做截断 + 摘要 + 关键片段，并保留 artifact / offset 供按需 poll、检索与 read-back。

04 · State & Memory记住什么、何时相信、断点后如何恢复，决定长程任务是否可靠。

崩溃恢复怎样不重复执行？

重连后，仅凭 transcript 无法判断真实环境已执行到哪里，极易重放具有副作用的动作。

信号：对话记录与真实环境状态不一致
治理：checkpoint 保存任务状态、已完成 action、外部 id、待确认项；恢复后先 re-observe。

记忆如何避免陈旧和污染？

旧事实、用户偏好、项目规则与模型推断若混在一起，错误记忆会长期支配后续决策。

信号：无来源旧结论覆盖新观察
治理：每条记忆带 source、time、confidence、scope、TTL；可撤销，并区分事实与推断。

多 Agent / 多渠道如何不冲突？

并发 session 修改同一文件、任务或外部资源时，状态覆盖和重复行动会迅速放大。

信号：并发编辑、重复提交、状态跳变
治理：session/task ownership、乐观锁或队列、branch/merge、actor 与 version 标记。

05 · Permission & Policy真正的难题不是“是否弹窗”，而是把最小权限和可理解的风险提示落到行动上。

审批阈值如何避免疲劳？

低风险动作频繁确认会让人盲点同意；阈值过高又会让危险外部操作无声通过。

信号：用户机械确认，或低风险任务频繁中断
治理：按目标、参数、环境、资源范围分级；确认页展示 diff、后果与可逆性。

如何防 prompt injection / confused deputy？

网页、代码、邮件等不可信文本会诱导 Agent 忽略规则，借其权限读取秘密或对外发送。

信号：外部文本要求越权、泄密或绕过确认
治理：标记不可信内容；最小权限与 capability isolation；敏感操作二次确认和 egress policy。

Sandbox & Isolation（隔离）如何设计？

Agent、工具与不可信网页/代码共处时，文件系统、网络、进程、凭据和子 Agent 的边界应如何划分，才能让一次越权不扩散为全局风险？

信号：工具默认继承宿主全部权限；不可信内容可触达凭据、网络或生产资源
治理：按任务启动最小权限 sandbox；隔离 cwd、凭据、网络 egress 与进程；用 capability token 传递授权，并为高风险动作设置独立执行环境。

06 · Verification & Recovery模型的自信不能当作证据；失败必须变成可行动的反馈。

谁来验证“真的完成”？

Agent 自评常把“我修改了”误当成“需求满足了”；尤其在测试、格式、外部系统与用户验收上。

信号：自信完成但缺 artifact / 测试证据
治理：独立 verifier：测试、schema、lint、diff、read-back 或受限的第二 Agent；输出证据。

验证失败如何改变下一步？

若失败只以自然语言返回，Loop 往往重复相同补丁，而没有定位失败处或缩小修改范围。

信号：同一测试失败反复出现
治理：结构化失败信息：位置、expected/actual、retry count、最小修复范围；将其写回 task state。

是否有回滚机制？

文件修改可借助版本控制撤销，但部署、数据库写入、消息发送等外部副作用未必天然可逆；Harness 必须提前界定恢复边界。

信号：改动范围膨胀；外部状态未知；失败后只能靠人工清理
治理：行动前 checkpoint / snapshot；对外部操作设计 idempotency、事务或 compensation；回滚后 re-observe 并输出恢复证据。

6. 源码对照：可靠性与治理（04-A–06-A）

聚焦长程状态、权限边界，以及验证和恢复闭环。

对自研终端 AI Agent 的 Skill 设计建议
  • 采用两阶段加载：启动时只进入 metadata；正文只在模型/用户选择后进入上下文。这是四个项目共同的 token 控制策略。
  • 把 Skill 当作“流程包”，而非“工具包”：Skill 应说明何时使用哪些工具、怎样验证、如何读取同目录资源；真正具备副作用的动作仍需经 Tool policy、权限与审批层。
  • 建立可解释的选择机制：记录 Skill 被谁、因何描述、在何轮加载；当任务失败时才能区分“模型未发现 Skill”“Skill 指令不完整”“工具不可用”。
  • 显式设计信任边界：项目本地 Skill、用户全局 Skill、远程安装 Skill 的可信度不同；至少需要大小限制、路径限制、frontmatter 校验和 prompt injection 检查。
对自研终端 AI Agent 的启示
  • 先确定边界：是做产品型 CLI（Claude Code）、Gateway/渠道层（OpenClaw）、可嵌入 runtime（Pi），还是持续自治平台（Hermes）。边界决定哪些能力应当内建。
  • Loop 可以很小，Harness 不能只有 Loop：四个项目都证明 Loop 不难；真正拉开差异的是上下文、工具策略、状态、权限和验证恢复。
  • 权限与验证必须显式选型：Pi 选择外包给 sandbox；Claude Code / OpenClaw / Hermes 则分别在 CLI、Gateway、平台中内建。没有“默认正确”的位置，只有与部署模型匹配的责任归属。
  • 推荐路线：以 Pi 式的清晰 core 为起点，优先补足项目需要的权限与验证闭环；需要多渠道、远程审批时再吸收 OpenClaw 的 Gateway 思路；需要长期记忆和自治任务时参考 Hermes。
